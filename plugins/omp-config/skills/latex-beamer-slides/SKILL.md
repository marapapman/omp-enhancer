# LaTeX Beamer Slides

When this Skill is part of a `writer` or `zh-writer` assignment, that invocation
(the dedicated language-matched text tool, hosted by its packaged Agent compatibility adapter) remains proposal-only: it runs no command and writes no file, and returns the complete proposed artifact or diff. Main or a separate explicitly capable Main-selected Agent owns authorized effects; that owner performs no prose drafting or revision, which belongs to the text tool alone.
## Text ownership and language

Before drafting or revising any text, Main identifies the target language from
the slide content (not from the instruction language); it calls the `writer`
text tool for English; Chinese text uses the `zh-writer` text tool.
Mixed-language decks run one text-tool pass per language slice. The invoked
`writer` or `zh-writer` text tool is the sole author of the Markdown content
plan and every title, body, caption, label, speaker note, narrative sentence,
translation, or rewrite. Main only forwards context and results, persists or
applies the complete writer proposal verbatim, and performs mechanical
non-text integration. Main must not draft, rewrite, translate, or polish any
slide text.
`task`, visual/layout agents, and reviewers may inspect text and report
findings, but must not write or modify prose, copy, labels, captions, notes,
or formulas. Text findings return to the corresponding `writer` or
`zh-writer` text tool; layout work never becomes copy editing. This is an
advisory ownership rule, not a router, lifecycle gate, retry policy, or
completion controller.

## Logic before style

Use this bounded writing sequence for the Markdown content plan and every
Beamer copy surface:

1. Main calls the language-matched `writer` (English) or `zh-writer` (Chinese)
   text tool, which proposes the complete text. The proposal establishes
   claims, evidence order, scope, and source basis before stylistic polishing.
   Mixed-language decks run one text-tool pass per language slice.
2. An independent checker may report logic, evidence, or style defects, but
   `task`, visual review, conversion, and Main do not rewrite prose. They return
   any wording finding to the corresponding `writer` or `zh-writer` text tool.
3. Any substantive wording repair, rewrite, translation, or polishing is
   generated by a new `writer` or `zh-writer` text-tool call. Main applies the
   complete writer proposal verbatim rather than combining fragments or making
   local edits.

## Copy bans

Across slide titles, body text, captions, labels, speaker notes, and narrative
text, ban reader-facing stage announcements, including the English examples
`The real question is`, `A new question is`, `This raises a deeper question`,
and `Let us turn to`, and the Chinese examples `新的问题是`, `真正的问题是`,
`这就引出了一个更深的问题`, and `接下来我们看` when they only announce a
stage. Also ban hollow or unsupported abstract significance claims such as
`this is important/significant/transformative`, `this demonstrates the power/value`,
`意义重大`, `具有重要意义`, `标志着`, `彰显了`, `开创了`, and `充分说明`.
Keep an importance or evaluation claim only when the same text states its
concrete result, scope, or source; otherwise replace it with that evidence or
with a stated limitation.


Choose the generation or modification path from the requested operation. Do not run generation-only interviews during an ordinary modification.

Agent availability and capacity remain Main decisions. `task` is a soft candidate when currently exposed and a safe complete assignment can be formed. Its absence, an unavailable renderer, or review findings are limitations to report, not plugin-owned completion permission. No review finding grants permission to convert, publish, or complete.

## Apply shared rules

1. Read the project instructions, exact Beamer entry point, local theme files, frame sources, assets, and native build commands before editing.
2. Treat Beamer as a LaTeX format workflow. For an existing deck, choose Chinese or English writing skills from the body being changed, not from the instruction language. For a new deck, use the explicitly agreed output language.
3. Apply the language Skills already declared and loaded during `WORKFLOW PLAN + LOAD`. For Chinese, use `plain-chinese-writing` for natural sentences, `zh-format-humanizer` for evidence-based AI-like phrasing removal, and normally `zh-writing-review` for page-level clarity; include `zh-writing-polish` only for actual polishing. For English, use `format-humanizer` for AI-tell removal and `writing-review` for page-level review. Use broad checker skills only when the user requests that broader review or the text provides concrete evidence for it.
4. Preserve semantic anchors: qualifiers, modality, scope, negation, comparisons, causal direction, numbers, units, citations, identifiers, math, cross-references, commands, comments, labels, and revision markers.
5. Preserve escaped LaTeX text such as `\%`. Do not turn it into a comment marker or rewrite custom macros without need.
6. Do not invent facts, citations, results, logos, brand rules, or visual assets.

Apply the PLAN-loaded `skill://latex-beamer-slides/references/beamer-quality.md` before a template readiness check, generation pass, or rendered-slide QA.

## Generate a new deck

1. Inspect template readiness before drafting slide content. Identify the Beamer main file, theme and style assets, logo decision, aspect ratio, typography, color system, layout conventions, frame organization, compiler, and build command.
2. Have `task` run the smallest compile smoke test that demonstrates the configured template works. Treat a missing, ambiguous, unresolved, or non-compiling template as not configured.
3. If the template is not configured and its choices materially change the requested result, discuss only the missing choices with the user. Cover visual character, logo or explicit no-logo choice, aspect ratio, fonts, colors, title and section pages, header and footer, margins, content density, code and figure layouts, and source organization. Reuse choices already supplied instead of asking again; when the user authorized a plain/default template and the assumptions are safe, state them and proceed.
4. After the template path is committed, apply the PLAN-loaded `slides-storyline` method. Establish purpose, audience, duration, output language, key takeaway, evidence, and a numbered slide outline. Ask the user only when a missing choice materially changes the deck; otherwise state explicit assumptions and retain them in the text plan. If the Skill was recorded unavailable, use this bounded outline method directly and retain that limitation.
Text-only content lives in a Markdown content-plan file and uses the matching writer or `zh-writer` proposal as its canonical text.
5. **Phase 1: Text-only content.** Before adding images, authoring visuals, or performing layout, produce the text-only page draft in section-sized batches and discuss every page. Create or update a Markdown content-plan file (for example, <deck>-content.md) with one entry per page: title, narrative job, detailed body, evidence/source basis, and prose visual role. For each page, write body text, captions, and explanations as complete natural-language sentences or paragraphs. The Markdown content plan is the canonical content source. Do not create or edit Beamer .tex frames during this phase. Do not add images, author visuals, or perform layout before the user confirms the Markdown content plan. Do not replace body text with isolated phrases, keyword strings, or phrase-only bullet lists. For Chinese slide text, use the declared Chinese writing Skills and preserve facts, qualifiers, numbers, citations, and causal direction. Body copy obeys the same phrasing bans as titles: bullets and captions must not open with a label-colon lead-in ("方法：…", "Method: …"), the deck contains no "不是X，而是Y"/"not X, but Y" contrast-repetition construction, no page opens or closes with a one-sentence summary of itself, no defensive writing anywhere — no unsourced hedging qualifiers (可能/或许/possibly/perhaps/relatively), no boilerplate disclaimers, no over-attribution without citations, no apologia for limitations nobody asked about — and no "specifics then sweep" summary clause (a concrete clause followed by a sweeping whole "这些共同构成了……/Together, these ..." that adds no new fact); state the result and its actual scope. Discuss the draft page by page, revise the current batch from feedback, and wait for the user confirmation of the Markdown content before visual authoring.
The `writer` or `zh-writer` proposal is the canonical text for every page
title, body, caption, label, speaker note, and narrative sentence. Main only
persists or applies that proposal verbatim after the content discussion; it
does not draft, rewrite, translate, or polish it.

6. **Slide-order reconciliation.** After the user confirms the Markdown content plan and before Phase 2 visual authoring, launch a separate `task` to adjust the slide order on the Markdown content plan (the sole content source). The task reviews the full deck for content overlap between slides, keeps each content module semantically coherent with one main job per slide, and reorders pages so the overall sequence follows a logical progression from context to conclusion. The task also verifies the title rules: no page title uses the "XX：XX" two-part label pattern (label + colon + label, in either language), and reading all page titles in deck order forms a coherent, grammatical narrative; it also checks the body bans (no label-colon bullet lead-ins, no "不是X，而是Y"/"not X, but Y" contrast-repetition constructions, no opening/closing one-sentence summaries, no defensive writing, no "specifics then sweep" summary clauses). Title and body violations are content findings that return to the Markdown content plan with the user, never .tex edits. The task returns a proposed reordering with per-move justification; Main discusses material order changes with the user, applies the agreed reordering in the Markdown content plan, and only then enters Phase 2. If a crossing cannot be fixed by reordering or regrouping alone — for example, content duplicated across pages or a single module split across several pages — the task reports it, and the affected pages return to the Markdown content stage, are resolved and reconfirmed with the user, and only then proceed. Never reorder frames by editing .tex directly; the .tex files are regenerated from the reconciled Markdown plan.
The slide-order task may change only page order or structural grouping
metadata. It must not rewrite, shorten, translate, polish, or otherwise alter
any writer-proposed text. It reports wording findings back to the corresponding
`writer` or `zh-writer` text tool, whose replacement proposal Main may apply
verbatim.

7. **Phase 2: Visual authoring and basic layout.** Only after the slide order is reconciled, generate the deck from the committed template and outline. Translate the confirmed Markdown content plan into Beamer frames and then perform layout. Treat the Markdown file as the sole content source; the .tex files are derived layout artifacts, not a second content source. Keep the main file structural and use one frame file per slide when the project follows that layout. Mark generated frame files and delete or replace only files carrying that marker; never erase handcrafted frames merely because their names match a pattern. For every page, select or create a visual asset and establish the base composition. Asset branches: prefer official icons and assetseeker stock (Pexels and Pixabay need no attribution); use generated images (native generate_image, or bl image for Chinese-text rendering) only for pages whose confirmed visual role calls for them, store asset files under the deck assets directory, and record provenance per asset (source URL and license, or provider, model, prompt, seed) in the content plan. Generated assets may return as WebP, which XeLaTeX cannot include through \includegraphics; convert them to PNG or JPEG when the asset is stored. Do not rewrite, shorten, or add content in .tex during layout. Never convert phrases or keywords into body text as a formatting trick; keep the confirmed body text intact. Shorten or condense only by revising the Markdown content source first, discussing and reconfirming the affected pages, then re-translate the affected frames. If content or page structure must change later, return to the Markdown content stage, reconfirm, and regenerate before layout resumes. Keep one main job per slide and preserve the confirmed story and semantic anchors.
Phase 2 copies the confirmed Markdown text mechanically into derived `.tex`
frames and layout. The producing `task` may change only TeX structure,
placement, sizing, spacing, and other non-text layout properties; it must not
rewrite the approved text.

8. Have `task` compile with the native engine for enough passes to resolve navigation and references. Task renders every page and binds an initial PDF and current page images for the layout pass.
9. Perform the single read-only visual precheck with exactly one owner—`task` or Main—chosen by Main according to which completed the artifact and has native visual input—on this initial task-bound render. Use only the same current revision evidence and record only advisory findings with page, region, criterion, evidence, impact, and limitations. These findings are inputs to the layout pass; the precheck does not issue a final verdict or create another layout pass. If Main is that owner, its read-only inspection does not grant compile, render, edit, or reconcile ownership.
10. Have `task` perform the final layout pass across the deck. Correct text and image overlap, crowding, clipping, undersized text, cropped or distorted figures, inconsistent margins, weak alignment, and unclear hierarchy without changing the confirmed content. If an overloaded slide needs splitting, return that content decision to the Markdown content plan, obtain user confirmation, and regenerate the affected Beamer frames before layout resumes. Never split, rewrite, or shrink slide content directly in .tex as a layout fix.
11. Have `task` recompile and render that exact layout revision, checking it against the committed outline, output language, source facts, semantic anchors, and LaTeX structure. Task binds one revision identifier, the PDF, the render directory, fresh renders of every page, and an overview or contact sheet. Do not review stale or mixed-revision evidence.
12. Confirm the basic layout with the user using the current task-bound PDF and page renders. Treat this as a separate conversational scope checkpoint after the first complete layout, before the existing visual review and refinement path. Do not enter layout refinement with unresolved user direction about the base composition.
13. **Existing visual review and refinement path.** This path preserves the current multi-pass visual evidence chain and remains advisory rather than an automatic repair controller. Perform the single read-only visual review of the latest rendered pages and overview with exactly one owner—Main, or a task that did not produce the revision—for text and image overlap, crowding, clipping, undersized text, image treatment, margins, alignment, whitespace, hierarchy, and cross-slide consistency. Record advisory findings only. For a supported finding, `task` applies the bounded layout-only source revision, rerenders it, and the review owner examines only fresh rerendered evidence, at most once for that changed revision. If a finding requires content or page-structure changes, return to the Markdown content plan, obtain user confirmation, and regenerate the affected Beamer frames before layout resumes.
14. **Optional PPTX output.** After the final validated Beamer visual revision for a new deck, if PowerPoint output is requested, apply the PLAN-loaded `beamer-to-powerpoint` Skill by following the optional PPTX output branch below. This branch does not replace Beamer review and does not permit content or page-structure edits.

No review finding grants permission to convert, publish, or complete.

Main only authorizes external effects during initial setup and accepts final delivery; it does not compile, render, modify, reconcile, or mediate the visual loop.

Keep unresolved material template, text, and layout choices visible. Ask the user only when a missing choice materially changes the deck; the text and basic-layout confirmations above are REQUIRED conversational checkpoints. "Not plugin-owned gates or completion conditions" means the runtime never blocks you — it does not mean the confirmations are optional. Skipping either confirmation without a stated reason is a workflow violation; report it in the final delivery.


## Optional PPTX output branch

For either a new deck or an existing deck, enter this branch only after the final validated Beamer visual revision and its current PDF and page-render evidence are complete. PPTX output is optional; do not convert every Beamer deck automatically.

1. Apply the PLAN-loaded `beamer-to-powerpoint` Skill with the fixed external `beamer2pptx` Skill/repository: https://github.com/xdmlxdml/beamer2pptx/tree/main/beamer2pptx. Provide the final validated Beamer PDF and the corresponding `.tex`, macro, and font sources when available. Do not ask for, require, or invent a user-supplied conversion command, and do not substitute another converter. Conversion is read-only with respect to the Markdown and Beamer content sources.
2. Dispatch one producing `task` to create, render, and bind one PPTX revision. Bind the exact input PDF, available source evidence, candidate `.pptx`, manifests or reports, and render directory to that revision. Use the existing OfficeCLI guidance where appropriate. Report package or structural validity, visual fidelity, and editability as separate results, do not claim any result that was not inspected, and do not treat OfficeCLI or a local package check as proof of Microsoft PowerPoint compatibility.
3. Main selects exactly one independent read-only PPTX visual-review owner: Main, or a `task` that did not produce this revision. The reviewer checks only the current PPTX renders and associated reports for slide count and order, text and formula editability where supported, clipping and overflow, missing content, unintended overlap, margins and alignment, hierarchy and typography, font substitution and legibility, aspect ratio and page geometry, raster versus vector treatment, and visible fidelity against the final validated Beamer PDF. Findings are advisory.
4. If the reviewer reports a supported layout defect, the producing task may apply at most one bounded layout-only fix to the editable PPTX. Preserve all visible content, formulas, slide order, and the Markdown and Beamer sources; adjust only placement, sizing, spacing, alignment, fonts, or equivalent layout properties. Rerender the exact changed revision and bind fresh evidence; the same reviewer confirms only those recorded findings once. Do not start an automatic repair loop, impose a hard gate, redispatch automatically, or review unchanged evidence.
5. If a finding requires rewriting content, changing a formula, adding or removing material, or splitting or reordering pages, do not patch the PPTX. Return it to the Markdown content plan and Beamer regeneration path. No PPTX review finding grants permission to convert, publish, or complete.

## Modify an existing deck

1. Read the exact requested frames and enough surrounding source to identify the current wording, language, macros, and visual conventions.
2. For any requested wording, translation, or prose revision, Main first generates the replacement text with a new `writer` or `zh-writer` text-tool call. Apply only the requested wording, language-norm, and existing-style changes through that text tool's complete proposal verbatim; Main and `task` must not draft, rewrite, translate, or polish the text.
3. Match the existing title pattern, terminology, capitalization, spacing, color roles, content density, and figure treatment. Preserve the story arc, frame order, template, logo, layout system, and unrelated content unless the user explicitly expands scope. Do not redesign the template or reopen story planning.
4. Compare semantic and LaTeX anchors once after editing. Have `task` compile and render the affected deck when a build is available, then identify the changed frames and any pages whose layout they can influence.
5. Perform the single read-only visual precheck with exactly one owner—`task` or Main—chosen by Main according to which completed the artifact and has native visual input—on this initial task-bound render, covering the changed frames and any pages whose layout they can influence; cover every page when a shared template, style, or macro changed. Use only the same current revision evidence and record only advisory findings with page, region, criterion, evidence, impact, and limitations. These findings are inputs to the layout pass; the precheck does not issue a final verdict or create another layout pass. If Main is that owner, its read-only inspection does not grant compile, render, edit, or reconcile ownership.
6. Have `task` perform a final layout pass on the changed frames and any pages whose layout they can influence. Correct text-box and image overlap, crowding, clipping, undersized text, cropped or distorted figures, alignment, and spacing while preserving every approved word, label, caption, formula, and note.
7. Have `task` recompile and render that exact layout revision, checking it against the requested semantic diff, LaTeX anchors, and authorized scope. Task binds one revision identifier, the PDF, the render directory, fresh high-resolution renders of every affected page, and a current full-deck overview or contact sheet. If a shared template, style, or macro changed, render and review every page.
8. Perform the single read-only visual review of the latest renders with exactly one owner—Main, or a task that did not produce the revision—for text and image overlap, crowding, clipping, undersized text, image treatment, margins, readability, and consistency with the existing deck. Record advisory findings only.
9. For a supported finding, `task` applies the bounded source revision, rerenders it, and the review owner examines only fresh rerendered evidence, at most once for that changed revision. Do not redispatch automatically or review an unchanged artifact. Report unresolved blocker or major findings honestly.
If any review or layout finding concerns wording, translation, or copy, Main generates the replacement text with a new `writer` or `zh-writer` text-tool call and returns to the Markdown content source. Do not resolve it in `.tex`; after a new proposal is approved, copy it mechanically and rerun the affected layout checks.
10. **Optional PPTX output.** After this existing-deck path reaches the final validated Beamer visual revision, if PowerPoint output is requested, follow the shared `## Optional PPTX output branch` above. PPTX layout fixes preserve visible content, formulas, slide order, and the Markdown and Beamer sources; content or page-structure findings return to the Markdown plan and Beamer regeneration path.

Main only authorizes external effects during initial setup and accepts final delivery; it does not compile, render, modify, reconcile, or mediate the visual loop.

Do not require template discussion or a story-outline checkpoint merely because an existing deck lacks a separate template manifest. Do not widen the edit to unrelated pre-existing layout defects. Do not split, add, remove, or reorder frames without explicit user authorization. Escalate only a concrete ambiguity that prevents the requested edit.

Report the main `.tex` file, generated or changed frame files, final revision identifier, output PDF, compiler command, render directory, layout and visual review evidence, and unresolved warnings. If conversion was requested, report the verified PowerPoint artifact separately.
